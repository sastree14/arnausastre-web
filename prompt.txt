Necesito dejar cerrado el sistema automático del LinkedIn Pack.

Problema actual:
El workflow intenta detectar artículos publicados usando la pestaña Articles Index o el campo Published, pero esto puede fallar porque después de hacer merge/publicar un artículo puede que Google Sheets no actualice correctamente Published = TRUE.

Objetivo:
El sistema debe detectar automáticamente qué artículos reales publicados en el repositorio todavía no tienen LinkedIn Pack, sin depender exclusivamente de Published en Google Sheets.

Arquitectura deseada:
1. La fuente principal para detectar artículos publicados debe ser el repositorio:
   - content/articles/*.mdx
   - Si el archivo existe en main, se considera candidato publicado.
2. Google Sheets Content Pipeline debe usarse solo como metadata complementaria:
   - Title
   - Industry
   - Theme
   - Role/Audience
   - Publication Date
   - Preview URL
   - Summary
   - Key metrics
3. El sistema debe comparar los slugs de content/articles/*.mdx contra los JSON ya existentes en:
   - content/linkedin/*.json
4. Si un artículo existe en content/articles/ y no aparece como source_article_slug en ningún JSON de content/linkedin/, entonces está pendiente de LinkedIn Pack.
5. Si hay varios pendientes:
   - Usar Publication Date de Content Pipeline si existe.
   - Si no existe, usar la fecha del frontmatter del MDX si existe.
   - Si no existe, ordenar por fecha de modificación/commit si es fácil.
   - Si nada funciona, ordenar por slug.
   - Elegir siempre el más antiguo.

Cambios concretos:
1. Modificar scripts/linkedin_pack/generate_pack.py y/o el módulo automático correspondiente para que mode=auto no dependa de Articles Index.
2. Leer directamente content/articles/*.mdx.
3. Extraer slug desde el nombre del archivo.
4. Extraer frontmatter del MDX si existe:
   - title
   - date
   - industry
   - role
   - theme
   - summary
   - key_metrics
5. Leer Content Pipeline en Google Sheets solo para enriquecer metadata, no como filtro principal.
6. Si Google Sheets falla, el workflow NO debe fallar si puede continuar leyendo content/articles/*.mdx. Debe emitir warning y continuar.
7. El workflow solo debe fallar si:
   - No existe content/articles/
   - No hay ningún artículo MDX válido
   - Gemini falla
   - El JSON generado no valida

Reglas de detección:
- Published en Google Sheets ya no debe ser obligatorio.
- Si Published existe y está en No/FALSE, no debe excluir automáticamente el artículo si el MDX ya existe en main.
- Si hay una columna Status/GitHub Status y dice Draft, puede usarse como warning, pero no como bloqueo si el archivo MDX existe.
- Articles Index debe quedar como fallback opcional, no como dependencia obligatoria.

Formato del LinkedIn Pack:
Mantener JSON estructurado en content/linkedin/.
Cada JSON debe incluir:
- campaign_id
- source_article_slug
- source_article_url
- title
- industry
- theme
- target_audience
- language
- status
- approved
- publish_mode
- created_at
- posts[]

Cada post debe incluir:
- day
- publish_date
- post_type
- title
- text
- image_required
- image_prompt
- image_path
- hashtags
- published
- published_at
- linkedin_post_url

Estilo de las publicaciones:
Quiero que el contenido sea útil para perfiles de dirección, CEOs, founders, operations managers y decision-makers.

No quiero posts técnicos para data scientists. Quiero posts que expliquen problemas de negocio con rigor, pero de forma fácil de interpretar.

Cada publicación debe:
- Tener un hook claro.
- Explicar el problema en lenguaje empresarial.
- Incluir KPIs o números aproximados cuando tenga sentido.
- Usar ejemplos simplificados pero creíbles.
- Hablar de impacto: coste, margen, capacidad, inventario, tiempo, riesgo, eficiencia o ingresos.
- Explicar la decisión que hay detrás del problema.
- Evitar humo de IA.
- Evitar promesas exageradas.
- No sonar como marketing vacío.
- No usar emojis.
- Usar 3-5 hashtags máximo.

Estructura semanal:
Lunes:
Contexto de la industria. Explicar qué tipo de empresas operan en esa industria, qué decisiones toman y por qué los datos importan.

Martes:
Problema principal. Explicar el fallo típico de gestión, proceso, datos o decisión.

Miércoles:
Caso práctico numérico. Crear un ejemplo simplificado con números aproximados y KPIs claros. Debe entenderlo un CEO sin background técnico.

Jueves:
Razonamiento consultor senior. Explicar hipótesis, diagnóstico y pasos generales para abordar el problema.

Viernes:
Resumen semanal + enlace al artículo completo. Extraer 3 aprendizajes principales y cerrar con una invitación suave a leer el artículo.

Prompt:
Actualizar prompts/linkedin_pack_prompt.md para reflejar este enfoque más ejecutivo:
- CEO-friendly
- KPI-driven
- decision-oriented
- operationally grounded
- technically rigorous but simple to understand

Workflow:
Actualizar .github/workflows/generate-linkedin-pack.yml para que mode=auto funcione sin inputs obligatorios.
Inputs:
- mode: auto/manual
- article_slug: opcional
- article_path: opcional
- publish_week_start: opcional
- language: default en
- dry_run: true/false

Si mode=auto:
- No pedir article_slug.
- Detectar automáticamente el próximo artículo pendiente.
- Calcular publish_week_start como el próximo lunes si está vacío.
- Si no hay pendientes, terminar correctamente sin crear commit ni PR.

Si mode=manual:
- Mantener funcionamiento actual.

Importante:
No publicar en LinkedIn todavía.
No tocar publish_linkedin.py salvo para mantener compatibilidad.
No romper el workflow editorial existente.
No depender de Articles Index.
No depender de Published = TRUE en Google Sheets.
El sistema debe estar preparado para que en el futuro, cuando tengamos API de empresa, solo activemos LINKEDIN_MODE=api y los secrets correspondientes.
